# iOSネイティブアプリ v1 構築 — 2026-06-19

## 背景 / なぜ

ユーザーから `/goal`: 「Web版と操作感が変わらない iPhone ネイティブアプリを作り、実際に本番
Cloudflare Workerバックエンドにリクエストして動かす。場所は既存システムと同じフォルダに置き、
一つの大きなプロジェクトのコードベースとして扱う」との指示。`~/Desktop/v-mate/ios/` に新規構築した。

## 技術選定

- **プロジェクト生成**: `.xcodeproj` を手書き/Xcode GUIで作らず、**xcodegen**(`brew`で導入済み)
  + `ios/project.yml` から生成する方式を採用。再現性があり、設定差分がレビューしやすい。
  生成後の `VMate.xcodeproj` は**そのままcommit対象**(xcuserdataのみ`.gitignore`)。
- **言語/UI**: Swift + SwiftUI、iOS 16+。
- **通信**: `URLSession`(`HTTPCookieStorage.shared`)。Web版と同じ匿名Cookie(`aikata_uid`,
  HttpOnly)方式がそのまま機能する——ブラウザ専用の仕組みではなく標準HTTPの仕組みなので、
  ネイティブクライアントでも自動的にCookieが永続化され、アプリ再起動後も同じ「シロ」を維持できる。
- **チャットSSE**: `URLSession.bytes(for:).lines` で `data: {json}\n\n` 形式を行ごとに解析。
  Web版 `frontend/src/features/chat/api.ts` の `streamChat` と同じワイヤ形式・イベント種別
  (emotion/token/done/error)をそのまま読む。
- **音声**: `AVAudioPlayer`(`isMeteringEnabled=true`)で `/api/tts?text=&emotion=` のMP3を再生し、
  `averagePower(forChannel:)` を 0..1 に正規化して `mouthLevel` としてアバターに渡す
  (Web版の `AnalyserNode` ベースのリップシンクと同じ役割)。

## 3Dアバター: WKWebViewでWeb版のthree-vrmビューアを再利用(重要な設計判断)

最初はSceneKit/RealityKitでVRMをネイティブに再実装する案も検討したが、**Opusアーキテクトに
正式に設計判断を委任**した結果(2026-06-19、planner/architectエージェント実行)、以下の理由で
**既存の `frontend/src/features/vrm/viewer.ts`(three.js+@pixiv/three-vrm、チューニング済み)を
WKWebView越しに再利用する方式**を採用した。

- `viewer.ts` は視線/まばたき/リップシンク等が実際の見た目で細かくチューニングされた約570行
  ([[gaze_conversation_stare_fix]] 等で継続調整中)。Swiftで再実装すると**同じ調整ロジックを
  2言語で二重管理**することになり、将来の調整が片方にしか反映されない不整合リスクが大きい。
- RealityKitはVRM/glTFのランタイム読み込みを直接サポートしない(USDZ変換が必要で、VRM特有の
  表情ブレンドシェイプグループが失われる)。SceneKit+GLTFKit2は技術的に可能だが、VRM拡張
  (humanoidボーン・表情プリセット)を独自実装する必要があり工数が大きい。

### 実装

1. `frontend/src/ios-avatar/entry.ts` — `CompanionViewer` をそのままimportし、
   `window.vmate.{setEmotion, setMouthLevel, notice, setAffinity, relax}` を公開する
   最小エントリポイント(フルSPAではない)。
2. `frontend/public/ios-avatar/avatar.html` + `npm run build:ios-avatar`(esbuild、IIFE)で
   生成する `avatar.bundle.js` を `frontend/public/ios-avatar/` に配置。
   **`public/` 配下に置いたのは、Viteの `build`(`emptyOutDir:true`)が `public/*` を
   `backend/static/` へ自動コピーする既存の仕組みにそのまま乗せるため**——ここに置かないと
   次の `npm run build` で消える。`package.json` の `build` スクリプトを
   `build:ios-avatar && tsc -b && vite build` に変更し、ビルド時に必ず再生成されるようにした。
3. **CORS問題の発見と解決**: 当初 `avatar.html` をiOSアプリにバンドルし `file://` から
   `https://aikata.../models/shiro.vrm` をfetchする設計を考えたが、クロスオリジンになり
   CORSヘッダ無しでブロックされるリスクがあった。**`avatar.html`/`avatar.bundle.js` も
   本番Worker自身(`backend/static/ios-avatar/`)から配信し、`/models/shiro.vrm` と同一オリジンに
   する**ことでCORSを完全に回避し、かつ**iOSアプリ本体には17MBのVRMモデルを一切バンドルしない**
   (実機確認済み: 同一オリジンで200、CORSエラー無し、実際にモデルが描画された)。
4. Swift側: `ios/VMate/Sources/Avatar/VRMAvatarView.swift`(`UIViewRepresentable`)が
   `https://aikata.taku810616.workers.dev/ios-avatar/avatar` を読み込み、
   `CompanionViewModel.currentEmotion` / `avatarMouthLevel` の変化を `evaluateJavaScript` で
   `window.vmate.*` に橋渡しする。読み込み失敗時は `@Binding var failed` で v1のシンプルな
   SwiftUIアバター(`AvatarView.swift`)へ自動フォールバックする。

### ハマりどころ

- **Cloudflare Workers の静的アセットは `.html` 拡張子を自動的に「きれいなURL」へ307リダイレクト
  する**(`/ios-avatar/avatar.html` → `/ios-avatar/avatar`)。Swift側は最初からリダイレクト後の
  URL(拡張子無し)を直接指定し、不要な往復を避けた。
- xcodegenは `project.yml` 変更だけでなく**新規Swiftファイル追加時にも `xcodegen generate` の
  再実行が必要**(ソースリストはgenerate時点でスキャンされるため)。Avatar/ディレクトリを
  後から追加した際にこれを忘れて `cannot find 'VRMAvatarView' in scope` で一度ビルド失敗した。
- `try? await someFunc()` で `someFunc` の戻り値が既に `T?` の場合、Swiftは結果を `T?` に
  フラット化する(`T??` にならない)。`guard let result = try? ..., let data = result else`
  のように二重にunwrapしようとすると `data` 側で「Optionalでない型に対するconditional binding」
  というコンパイルエラーになる。`guard let data = try? ... else { return }` の一段で十分。

## 検証(実機相当: iOS Simulator + 実際の本番Cloudflare Worker)

- `xcodegen generate` → `xcodebuild`(MCP経由)でビルド成功。
- シミュレータで実際に起動し、起動直後に **本番 `/api/research/session` → `/api/state` →
  `/api/nudge`(greeting)** が実行され、実際のLLM生成の挨拶文が表示されることを確認
  (スクリーンショットで確認)。
- チャットのSSE解析ロジックは、アプリ内蔵の `APIClient.streamChat` と同一パターンの
  スタンドアロンSwiftスクリプトを本番に対して実行し、`emotion`/`token`/`done` イベントが
  正しく解析されることを確認(`status:200`, 実際の応答テキスト受信)。
- **3Dアバターが実際にWKWebView内にレンダリングされ**、透過合成・感情に応じた見た目・
  本番チャット履歴との統合をスクリーンショットで確認(Web版と同一の「シロ」キャラクター)。
